- src/pages/book.tsx

--------------------------------------------------
1. CURRENT PROBLEM
--------------------------------------------------

When a customer clicks "Book" for a treatment from the Services page, they arrive at a URL such as:

/book?treatment=The%20Glow

The treatment is already known from the URL.

However, the booking page currently makes the customer interact with the treatment selector/list and scroll through treatments.

I do NOT want this.

If the customer arrived from a specific treatment's Book button, they should immediately see the treatment they are booking and move on to selecting their date.

--------------------------------------------------
2. NEW EXPERIENCE WHEN A TREATMENT IS ALREADY SELECTED
--------------------------------------------------

When the URL contains a valid treatment parameter, for example:

/book?treatment=The%20Glow

DO NOT display the full treatment list as the first thing the customer sees.

Instead, display a compact selected-treatment summary.

The layout should communicate:

BOOK YOUR APPOINTMENT

You're booking

[ The Glow ]

[ existing price ]

[ Change treatment ]

Then immediately below that:

SELECT YOUR DATE

[ existing calendar ]

The customer should NOT have to:

- open a dropdown
- scroll through treatments
- search for the treatment they already selected
- select The Glow a second time

The selected treatment should be obvious immediately.

Use the existing treatment data from:

src/lib/treatments.ts

Do NOT manually hard-code treatment names or prices.

--------------------------------------------------
3. "CHANGE TREATMENT" FUNCTION
--------------------------------------------------

Add a clear but secondary action:

Change treatment

When the customer clicks "Change treatment", DO NOT navigate them away from the booking page.

Instead, open a treatment-selection interface as a modal/overlay, drawer, or expandable panel.

Choose whichever approach fits the existing Sediba design and existing React structure best.

The important behaviour is:

DEFAULT STATE:
Show only the selected treatment.

AFTER "CHANGE TREATMENT":
Show the treatment-selection interface.

This prevents the long treatment list from taking up the booking page when it isn't needed.

--------------------------------------------------
4. TREATMENT PICKER
--------------------------------------------------

Inside the Change Treatment interface, the customer should be able to browse and select another treatment.

The picker should include:

- Search treatments field
- Existing treatment list
- Existing treatment names
- Existing prices
- Existing descriptions where available

Search should filter the existing treatment data.

Search should be optional.

The customer must still be able to browse treatments.

Do NOT force the customer to search.

Use the existing treatment data as the single source of truth.

Do not duplicate the treatment list in another file.

--------------------------------------------------
5. AFTER CUSTOMER CHANGES TREATMENT
--------------------------------------------------

If the customer selects another treatment:

- update the selected treatment
- close the treatment picker
- show the newly selected treatment in the treatment summary
- update the displayed price using the existing treatment data
- continue with the existing booking flow

For example:

Initially:

You're booking

The Glow
R___

Change treatment

After selecting another treatment:

You're booking

Deep Release
R___

Change treatment

The customer should then continue to the existing date/calendar section.

Do NOT make them go through another treatment-selection step.

--------------------------------------------------
6. DIRECT /book VISIT
--------------------------------------------------

There is another scenario:

The customer visits:

/book

with no treatment query parameter.

In this case, there is no treatment to display.

Show a clear treatment-selection state.

For example:

BOOK YOUR APPOINTMENT

What would you like to book?

[ Choose a treatment ]

Clicking this should open the same treatment picker described above.

Therefore there should be ONE treatment-selection component/interface used in both situations.

Do not create two separate treatment systems.
