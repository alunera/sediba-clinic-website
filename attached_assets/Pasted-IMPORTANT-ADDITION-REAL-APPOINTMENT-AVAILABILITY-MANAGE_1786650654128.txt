IMPORTANT ADDITION — REAL APPOINTMENT AVAILABILITY MANAGEMENT

The calendar must NOT use hard-coded available dates.

Sediba Wellness needs a real availability-management system where the salon/consultant can control which dates and times customers are allowed to book.

The consultant should be able to manage availability from the existing admin/back-end system.

CORE REQUIREMENT:

The availability entered/changed by the consultant in the backend must directly control what customers see and can select on the public booking page.

The system should work like this:

CONSULTANT / ADMIN
↓
Creates available appointment dates and times
↓
Availability is saved in the database
↓
CUSTOMER
↓
Opens booking page
↓
Calendar retrieves current availability from the database
↓
Only available dates are selectable
↓
Customer selects a date
↓
Only available time slots for that date are displayed
↓
Customer selects a time
↓
Customer completes booking
↓
The selected date/time becomes unavailable for another customer once successfully booked

IMPORTANT:

Do NOT hard-code availability into the frontend.

Do NOT create fake available dates just to make the calendar work.

The frontend must read availability dynamically from the backend/database.

ADMIN AVAILABILITY MANAGEMENT:

Inspect the existing admin/back-end functionality and determine whether there is already an availability-management component.

If one exists, reuse and improve it rather than creating a duplicate system.

If it does not exist, implement a simple availability-management section within the existing admin system.

The consultant/admin should be able to:

1. View a calendar of upcoming dates.
2. Mark a date as available.
3. Mark a date as unavailable.
4. Add available time slots to an available date.
5. Remove individual time slots.
6. See which time slots are already booked.
7. Prevent already-booked slots from being offered again.
8. Modify future availability without changing code.

Example:

Admin selects:

August 20, 2026

and adds:

09:00
10:30
13:00
15:00

The customer-facing calendar should then show August 20 as an available date.

When the customer selects August 20, the frontend should show:

09:00
10:30
13:00
15:00

If the consultant later removes 13:00 from the backend, the customer-facing booking page must stop showing 13:00.

If another customer books 10:30, that slot must no longer be available for another customer.

DATABASE:

Use the existing database architecture.

Before creating anything new, inspect the existing database/schema and booking implementation.

Create or update the minimum required data structures for:

- availability dates
- availability time slots
- bookings/reservations
- booking status

Do not create duplicate booking or availability systems.

AVAILABILITY LOGIC:

The frontend should retrieve availability dynamically.

For each date:

IF the consultant has configured available slots
→ date is selectable

IF no availability exists
→ date is unavailable

IF date is in the past
→ date is unavailable

IF all slots for a date have been booked
→ date should become unavailable

When a customer selects a date:
→ retrieve the current available time slots for that date.

Do not rely solely on frontend validation.

The backend must also validate that the selected slot is still available when the booking is submitted.

This is important to prevent two customers from booking the same appointment simultaneously.

BOOKING FLOW:

The complete flow should now be:

1. Customer visits Services page.
2. Customer clicks Book under a treatment.
3. Customer arrives at /book?treatment=...
4. Treatment is pre-selected.
5. Customer clicks Continue.
6. Calendar displays real availability retrieved from the backend.
7. Customer selects an available date.
8. Available time slots for that date appear.
9. Customer selects a time.
10. Customer enters their details.
11. Backend checks that the selected slot is still available.
12. Booking is created.
13. The slot is marked/reserved as booked.
14. Customer receives the confirmation.
15. The booked slot disappears from available slots for future customers.

ADMIN EXPERIENCE:

The consultant should not need to edit code to change availability.

For example, if the consultant knows that she is available on:

August 20
August 22
August 25

she should be able to enter those dates in the admin interface and the public calendar should automatically update.

If she later decides she is NOT available on August 22, she should be able to remove/block that date in the admin interface and it should immediately become unavailable on the customer-facing calendar.
